# BIOS 问题调查方法

目标：给出**可复核**的调查结论；根因未知就保持未知，不用"看起来合理"的解释凑结论。

## 四步法

1. **症状取证**
   - 先固定"观察到的现象"：什么条件下、哪个阶段、可复现还是偶发、有没有日志/串口/后码。
   - 把"用户描述"和"代码事实"分开放：用户说"USB 只有 2.0"是**现象**，不是根因。
   - 只读调查也算进展：不是修改了代码才有值得保存的结论。
2. **范围收窄**
   - 用阶段判定把范围缩到最小（见 `common-uefi` 的定位顺序），再读**有界**的少量文件。
   - 一个症状可能有多个候选路径（配置、库实现、板级覆盖、上游默认值）；**并列保留**，不提前选一个。
3. **根因假设**
   - 每个假设必须写出"支持它的证据"与"能推翻它的观察"。
   - 冲突的候选不合并；不知道就写 `unknown` 并列出还缺什么资料。
4. **验证分层**
   - 代码走查 → 编译 → 上板启动 → 循环/压力 → 客户验收，是**五种不同强度**的验证；
     有源码依据不等于编译通过，编译通过不等于板卡通过。
   - 没有真实执行的验证，一律不写入验证记录。禁止把"测试命令没报错"写成"板卡验证通过"。

## 保存纪律（默认自主工作流）

- **不要要求用户说"建任务/记住/保存"**：宿主已授权时，扩展会自动准备背景并做本项目线索检索；
  有意义进度用 `bios_manage_task` 保存，调查结论用 `bios_save_experience_draft` 存为**草稿**。
- 任务进度与草稿是两种记录：进度写任务，结论写草稿；回链失败时如实报"经验已保存，任务关联待重试"，
  不整体说未保存，也不重复建卡。
- 本项目草稿只作为**未验证线索**参与后续检索，不能进入当前推荐块，也不能作为移植决定、
  客户要求或测试通过的依据。
- 只读调查若不足以确认根因，就保存 `unknown`/待验证，而不是凑一条经验。

## 边界

- 用户说"先不要改代码"时只做只读调查；自动记忆许可**不**授予额外源码修改权限。
- 不执行来源不明的 build/flash 脚本；不做自动提交/推送。
- 不因为工具调用成功就宣称根因正确或工程完成；"回答完成"不等于"任务完成"。
