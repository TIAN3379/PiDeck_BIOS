## 2. 节点 A：D2R 完成标准

完整阅读验收 §3；四组一起修，保持 D1 103 项与 D2 正常路径、真实双进程竞争。

### A1：目标边界与归属（D2-1）

- 目标父链按原方案拒绝链接；canonical 重叠判定保持，不靠词法 startsWith。
- 目标根与子目录/文件取得时登记可核对身份，写入/读取/发布/清理前检查相关祖先和类型；不能把“路径曾由我创建”当作当前仍归我所有。
- 新目录 EEXIST 明确冲突，不能无条件接纳或登记为本次创建。目标被移动、替换成 junction 或同名其它文件后，拒绝/保留，不往替换物里写，不删除替换物、根外 sentinel 或竞争进程产物。
- 不 recursive 删除调用方路径；对归属不明的整个受影响分支停止清理，附有界、结构化残留状态。可清理其它已证明自有分支，但不得穿过未知祖先。
- 新增真实 junction 替换回归，至少证明 outside sentinel 和 replacement 保持。可验证元信息检查不宣称 OS 沙箱或无 TOCTOU；但不能只改文案回避已复现的删除。

### A2：完整目标集合（D2-2）

- 按预算盘点容器根与 data 下实际文件、目录、类型和唯一集合；与 manifest 全量比对，不只逐个打开声明文件。
- 额外文件/目录、缺失文件/空目录、链接、未知根条目都不能发布完成标记；不要静默删除未知内容来让检查通过。
- 额外文件属于未知归属：失败时保留它和必要祖先，报告残留，不要求无条件“删干净”。测试断言据此调整，但不放宽虚假成功保护。
- manifest 自有临时文件按阶段和身份单独处理，首版不接受任意遗留 `.tmp`。

### A3：提交和清理事实（D2-3）

- 根 mkdir、目录 mkdir、文件 open 成功时即登记归属；包括等待中取消/失败。正常写入和 close 成功后才可进入发布，失败路径尽力关句柄，保留首错。
- 关键等待/hook 后复查取消，尤其实际 link 前。link 成功才是 D2 提交点；之后迟到取消不伪称回滚。
- manifest 临时文件从创建起纳入清理；写/短写/sync/close/hook/link 失败都走同一生命周期，硬链接不支持受控失败，不回退直写。
- 清理事实为结构化字段：主 code、受控 phase、published、cleanup 和有界残留/警告。可扩展 backup 窄结果或 StorageError 的可选元信息，保持旧调用者兼容，不能只拼在 message 中。确定 API 后写实施记录。
- 取消也保留 cleanup 事实；提交后 unlink(temp) 失败必须 published=true/cleanup=failed，不能回滚完成备份或返回 cleanup=ok。
- 为短写、sync/close、发布失败、清理拒绝、根取得取消、发布前取消和发布后迟到取消补真实 IO 注入测试，明确 open/close 生命周期。现有 `ioHooks.link/closeFile` 如要用于 backup 必须实际接入；只加接口不接代码不是覆盖。

### A4：公共错误（D2-4）

所有入口阶段都统一映射受控、有限诊断，不论有没有取得目标、不论清理成功与否。原始 Error、FS cause、源绝对路径、未知条目名和正文不能从 backup 公共 API 返回。允许调用方显式给出的目标路径，定位优先已知相对落点/阶段。

保持主错误类别与补充 cleanup 信息；不能把每个失败都压成 unknown。测试原始错误带敏感标记、源超限真实错误、非法根/父目录、取消与清理失败，检查返回/抛出对象而不只检查打印文本。

原 D2 必测而未覆盖的预算 0/精确/差一、源增删/目录/同长度变化/末次锁、读取增长、预检截断/裁剪一并补在本批，不新增独立整改轮。读取前后可用身份/大小/修改信息与 hash 检查保持观察式，不承诺捕获全部 ABA。

## 3. 节点 B：D3 最小 API 和准入

建议窄入口 `restoreKnowledgeBackup({ backupRoot, root, offlineConfirmed: true, limits?, preflightLimits?, signal?, ioHooks? })`，通过 backup/index 对外。最终签名/状态表记入实施记录。

- `backupRoot`：显式完全限定的已完成备份容器；不是 data 子目录。容器根、data 和内部路径不接受 symlink/junction，父链按 A1 口径验证。
- `root`：显式完全限定、**尚不存在**的新知识根，父目录必须已存在。“恢复到新空目录”指由本次排他创建的新目录；已有空目录也拒绝，不复用、覆盖或合并旧库。
- `offlineConfirmed:true`：调用者确认备份容器不被修改、目标不被其它进程使用；在任何目标创建前检查。
- 拒绝源/目标相同、互相包含、canonical 别名重叠。已有目标的文件/目录/半成品/链接一律保护；不得创建任意父链。

取得目标前按顺序检查备份：

1. 有界读完整 `manifest.json`，校验 backupVersion、严格字段/落点/预算；未来版本拒绝，不转换、不自动修补。
2. 有界盘点容器的真实唯一集合（根仅 manifest/data），与清单文件/目录/类型完全匹配；未知条目、tmp、链接、缺失或重复别名拒绝。
3. 原字节核验长度/SHA-256，复用 D1 判据；校验通过不等于业务版本可解释。
4. 复用 `inspectKnowledgeStore` 检查 `backupRoot/data`：完整、no-migration-needed、无截断/裁剪/阻断/人工事项。cache/locks 缺席是 D1 明确排除，按现有预检可选语义处理，不改 C3 放宽其它准入。

坏 JSON、未来业务/工件版本、prepared/conflict、身份/归属冲突及现有预检不能解释的内容都拒绝正常恢复。无签名的 hash 不证明可信来源；首版只做声明的本地备份完整性和当前版本准入，不增加认证系统。

## 4. 恢复、完成点与失败边界

复用 A 节修正后的目标取得/身份检查/有界 IO/清理，不再写一套放宽原语。若抽共用模块，保持旧 exports，不为备份重构整个 Boundary。

- 排他创建新 root；按 manifest 保留所有已知空目录，另创建**空** cache/locks。不要复制任何旧锁或缓存；registry 的绑定信息、记录 ID/revision/time、journal/audit 原字节不改。
- 除 registry 外逐文件复制并回读；总量按实际字节安全累加。复制顺序不依赖调用者排序；目录父子关系由已验证落点派生。源和目标不无界累积整库。
- registry 原始字节留作最后发布。所有其它文件/目录和空 cache/locks 的完整集合、长度/hash及归属核对成功后，重新核对备份容器集合/内容/业务准入，再非覆盖发布完整 registry（temp/sync/close/link）。
- **registry 非覆盖发布成功为 D3 完成点**；之前新目录可见但缺 registry，不宣称已初始化。不得调用 initialize 先发布空 registry 再填数据，也不写 backup manifest 到知识根来改变布局。
- 发布后使用现有读取/预检确认库可解释。若发布后检查/取消/清理出现问题，报告“已提交，需复核/存在残留”，不得删掉已恢复库或伪称未写入。仅验证成功才返回无警告 restored；明确 committed-needs-review 等状态，不把提交事实与验证事实混为一谈。
- 失败前的目标按归属精确清理；未知/替换分支保留并结构化报告。备份容器和原库全程只读，不删源 manifest、锁或残留，不自动 reconcile。
- 不引入跨平台原子目录 rename 服务。本方案只承诺 offline-copy 和可验证发布点，不承诺网络盘/断电原子恢复或同机恶意写入者隔离。

复核不能仅证明“后一次源 hash 等于前一次复制 hash”，同时忽略业务准入时读到的不同字节。各阶段保存必要指纹/身份并复核；发现可观察变化即拒绝。原方案两套限额各自生效，明确实际范围/阶段预算；0 不变成 unlimited，精确上限可接受，差一受控拒绝。

registry 中原来的绝对工作区绑定原样保留，**恢复知识库不迁移 BIOS 源码、不重新绑定路径，也不证明原路径仍在线/适用于本机**。实施记录说明此边界，后续 BM-03 人工确认处理；不要为了“可用”静默重写客户项目身份。

### 8.2 接续节点 B，不重新设计业务范围

按本文 §3～5 与 [实施记录 §6](bm02d3_implementation.md#6-断点交接节点-bd3-剩余步骤)继续 restore API、backup/index 出口和恢复测试。注意三处真实复用差距：

1. 备份侧读取不是“自有写入会话”；实际常规类型、祖先/根链接、identity 和变化核对由只读容器边界负责，不能只用 open/fstat 宣称拒绝链接。

### 11.2 D4 最小命令契约

计划入口 `packages/bios-agent/cli/knowledge.mjs`，Package 增加 `knowledge` script；以下均是待实现契约，不是当前可执行命令。沿用 Node 24 与现有 TS 加载方式，无需引入 CLI 框架。

| 命令 | 参数与行为 |
|---|---|
| `--help` | 列出命令、参数、离线声明及局限；不读取知识库、不创建文件 |
| `inspect --root <绝对路径> [--json]` | 调用现有只读预检；输出有界结论、数量、截断/人工事项，不输出业务正文 |

所有命令显式给路径，不回退到默认真实用户库。写命令同时要求离线声明与写入确认，缺任一项在调用写 API/创建输出前拒绝；不弹交互输入，不自动确认或删锁。未知、重复、缺值或不合格参数受控拒绝；选项不允许重复值覆盖。CLI 沿用 API 默认限额，首版不加无限制开关。

退出码约定：`0`=成功且无清理/预检/复核问题；`2`=命令/参数错误；`1`=操作拒绝、取消或预检不完整/有阻断人工事项；`3`=已发布/已提交但存在残留或需要复核。不能把所有“函数返回”都记成 0。发布事实存在时，错误输出也必须保留它，不能让调用者误以为没有写入。

`--json` 的 stdout 只放一个有界结果对象；诊断走 stderr。结果保留 status/code、阶段、published/committed、cleanup、受控残留与预检完整性，不透传 stack、原始异常、正文或未知条目名。help 可展示用户参数含义，不把预检变成知识正文 dump。
