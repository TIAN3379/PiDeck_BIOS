## 2. 阻塞项

### A1 / P1：恢复先写终态，可能永久丢失审计

证据：[实施记录](bm02c2a_implementation.md) §3.1 的正常写入是“事件 → journal 终态”，但 §3.3 明确要求“先收口 journal，再考虑补发”，窗口表也先记 committed。相同表又规定“已有终态不补发事件”。

按该恢复协议：记录已是 after、事件缺失 → 恢复器写 committed → 补发前再次中断 → 下次看到终态直接返回。事件永久缺失。现有 C1 `reconcile.ts` 第 144/231 行对终态提前返回，不能先调用它再补审计。

修正判据：审核路径先持锁核对并发布/认领事件，成功后才写完成终态；事件失败仍可恢复，绝不把业务已提交说成未提交。列明恢复器自身再次中断的窗口。终态异常缺事件必须显式报不一致，不能沿用普通 v1 的无条件成功。

### A2 / P1：字节相同比对与发布来源语义互相冲突

证据：§3.2 把“同 eventId 且字节相同”作为幂等成功条件；§3.4 又要求补发使用 `publication=recovery` 与实际 `recordedAt`。§3.8 甚至把恢复结果的 publication 固定为 recovery。

writer 已发布事件但未写终态时，恢复器按 intent 构造的新事件会改变 publication/recordedAt，字节必然不同。恢复器第一次补发成功、终态前中断后，第二次补发时间同样不同。当前规则会误报冲突；把已有 writer 事件返回成 recovery 又会改写发布事实。

修正判据：不存在事件时才生成发布事实；已有事件需完整校验并与 intent 的不可变决定字段及关联逐项匹配，保留其原始 publication/recordedAt，不覆盖、不重新打时间。不同决定仍冲突。通过纯 helper 和永久测试固定比较规则，不只改文案。

### A3 / P1：缺失意图被当作普通写，缺少可验证关联

证据：§3.6 仅靠 intent 文件是否存在区分普通/审核写，缺失就按普通 v1 收口。没有明确 intent 与 journal 的 operationId、eventId、target、before/after、真实 intent 字节指纹如何交叉验证，也没有独立 intent 的可执行关联校验。

审核已提交后 intent 缺失，或旧 C1 恢复器不理解 companion 文件，都可能把审核 journal 当普通写收成终态，绕过审计。仅有同名文件或 `purpose=review` 不能证明它属于这次提交；错目标/错指纹意图不能据此发布人工审核事实。

修正判据：为未来审核 journal 设计明确版本与必填审核标识/关联，缺失、坏 JSON、未来 intent 版本或关联不一致都保守拒绝。建议未来审核专用 journal v2、普通写继续 v1；旧 v1 解释保持不变，旧恢复器拒绝 v2，不做自动迁移。本次只修协议与纯关联校验，不实现 journal v2 IO。
