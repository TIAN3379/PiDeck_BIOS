## 3. S1 · P2：未截断目录的观察成本延后到候选处理

位置：`core/storage/preflight/scan.ts` 的 `listEntriesBounded`（354 行起）和 `chargeEntry`（100 行起），以及 `categories.ts` 的 audit 父/子目录循环（319 行起）。

根因：只在 `listing.truncated` 时立即累加 `listing.scanned`。普通列举已经观察了整批名字，却仅在调用方逐个处理时记账。处理第一项就进入子目录或被输出预算打断，剩余名字的实际观察成本还没有进入总预算。

独立诊断用当前公开入口，临时包装真实 `node:fs/promises.opendir` 的异步迭代器：每次返回非 done 条目就计数，不改返回条目、读写内容或上限。包装只在一个独立 Node 进程中生效，结束后恢复。

### 场景 A：嵌套 audit 扫描超出共享预算

初始化合法库；创建 `audit/record-0`～`record-3` 四个受控目录，每个放十个 `event-0.json`～`event-9.json`，内容均为 `{}`。使用 `maxScanEntries=15`，其他限额默认。

实际：

```json
{"limit":15,"observed":18,"reported":16,"complete":false,"truncatedBy":["scan-entries"]}
```

父目录已观察 4 条，只先扣其中 1 条；第一个子目录观察/处理 10 条，再扣第二个父条目时账面为 12，于是第二个子目录允许观察 4 条（含探测）。实际是 `4+10+4=18`，超过约定的全局 `15+1`；报告却为 16。所有子目录形状相同，不依赖哪一个先被列出。

### 场景 B：输出停止后扫描统计低报

另一个合法库，在 `experiences/` 放十个受控 `exp-*.json`，内容 `{}`；设置 `maxOutputBytes=200`，条目限额默认。

实际：

```json
{"observed":10,"reported":1,"complete":false,"truncatedBy":["output-bytes"]}
```

目录早已观察十条，第一条候选的输出触顶后仅报告一条。`incomplete` 判定正确，问题是计数不真实，也不能供后续预算复用。

这不是要求新增“原子快照”或“全库一致性检查”，只是补完原 PF-4 的全局条目计量。下一轮需要在有界列举返回时就记录实际成本，候选处理不重复扣账，并让父目录剩余成本在进入子目录前已计入。
