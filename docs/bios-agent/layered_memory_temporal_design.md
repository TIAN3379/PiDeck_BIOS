# BIOS Agent：分层记忆与时态一致性设计

2026-10-07 状态：自主工作流已交付，当前行为见[技术架构](tech_design.md)。持久项目许可下自动准备/记账，明确继续且唯一候选任务时重读接续；本项目 draft 只通过独立 working 用途作为未验证线索，不改 current 推荐/M1 审核语义。下文范围、证据、时态、CAS、旧格式和关键确认要求保留。

设计日期：2026-10-02；状态更新：2026-10-07。M1 决策、项目/任务/知识业务、Pi 专业工具、生命周期和桌面 UI 已交付；正式 M2 历史/耐久指纹/迁移未实现，不能称模型自动训练或完整双时态记忆。

本设计补充[当前架构](tech_design.md)，不替换 Pi Package、JSON、revision、协作锁、journal 和审核底座。阶段编号保留用于理解设计依赖，不表示要求重新执行已完成的存储开发。

## 1. 要解决的具体问题

换对话能恢复当前任务，但不能恢复已经撤回的结论；历史项目经验可检索，但不能把另一个客户/板卡/分支的验证当成当前工程事实；同一需求发生变更后，要能解释“当时为什么这样做”和“现在应该按哪一版做”。

RAG 负责找候选材料，不负责决定材料是否有效。向量相似度、聊天摘要和较新的 `updatedAt` 都不能替代工程状态判断。首版继续关键词/别名检索，不新增向量服务、知识图谱或另一套 Agent 框架。

本期目标是本机可解释、可复核的记忆闭环，不承诺企业认证、任意工具外发防护或完整双时态数据库。

## 2. 分层与现有记录的对应

层级是职责划分，不是五套新数据库。

| 层 | 负责什么 | 存放/复用 | 不负责什么 |
|---|---|---|---|
| 工作记忆 | 当前一轮的目标、相关事实、未决问题与预算 | Pi 当前上下文 + `ContextManifest` 来源清单 | 不成为工程事实唯一副本；压缩摘要不覆盖记录 |
| 任务记忆 | 需求、决策、待办、阻塞、状态、验证与交接 | `TaskRecord`，按 projectId/taskId/workspace 隔离 | 完成任务不自动批准经验，也不代表新基线已验证 |
| 项目记忆 | IBV/芯片/板卡/客户/CRB、构建入口、确认字段及证据 | `ProjectProfile` + registry 绑定 | 检测候选不自动覆盖人工确认；同远端不自动合并 |
| 复用记忆 | 问题根因、方案、适用边界、需求沿革与历史验证 | `ExperienceCard` + `FeatureRecord` + `EvidenceRef` | 搜索命中不等于可直接移植；历史成功不是当前成功 |
| 流程记忆 | UEFI/厂商工作方法、安全规则、调试/移植步骤 | 版本化 Skills 与明确的应用规则 | 不存客户事实副本；引用资料不能提升为系统指令 |

前三类业务记录与复用记录继续位于当前知识根。`cache/`、未来 embedding/全文索引、派生摘要均可重建；删除 Session 不删除工程知识。Skills 按需加载，不把所有 IBV/Silicon 规则同时塞入上下文。

## 3. “哪个事实可信”与“在哪个范围有效”分开

模型输出先作为候选。人工确认、审核和验证保持已有入口约束；`operatorLabel` 仍不是身份认证。现有 `draft/reviewed/verified/deprecated` 的含义保持，不用时态字段绕开批准。

需要分别判断四个维度：

- 来源与确认：候选还是人工确认，引用依据能否复核。
- 工程范围：项目/客户/平台/板卡/工作区/分支/代码快照/构建目标。
- 业务有效性：尚未生效、有效、被替代、撤回或存在冲突。
- 验证适用性：在哪份代码、哪个板卡版本、什么测试条件下，通过了哪类测试。

这些维度不能合成一个“置信度”。例如经验卡可以审核通过，但对目标板卡不适用；一项旧上板验证仍是真实历史证据，但不能证明当前 HEAD。

事实权威按内容划分：当前实现以目标代码快照为依据；客户需求以人工确认的需求版本为依据；项目身份以确认字段及其证据为依据；验证以具名测试记录为依据。相互矛盾就输出差异/待确认，不用来源数量或最新时间戳强行选胜者。

复用范围过滤先于返回标题、摘要、计数；模型端点使用许可另行检查。资料存本地不等于允许发给当前模型。跨客户授权不由模型推断，本设计也不声称限制 Pi 所有普通文件/终端工具。

## 4. 时间与因果模型

### 4.1 时间不能只有 updatedAt

以下是**后续契约候选字段**，不是现有 schema 已支持的 API；最终类型由 BM-M1/M2 明确。

| 信息 | 语义 | 示例 |
|---|---|---|
| `occurredAt` | 工程事件实际发生时间，可未知 | 9 月 20 日进行上板测试 |
| `recordedAt` | 知识库录入/收到该信息时间 | 10 月 2 日补录测试 |
| `effectiveFrom/effectiveTo` | 业务结论的适用时间区间，可未指定 | 新客户需求从 10 月 5 日生效 |
| `revision` / `expectedRevision` | 同一记录的因果顺序与写入冲突闸门 | 旧会话不能覆盖 revision 8 |
| `supersedes` / `retracts` | 明确针对哪个事实版本、何种范围的变更 | 替代 Board A 的需求 v1，不影响 Board B |

有效区间使用半开区间 `[from, to)`；未知不是无限有效或无效，不从 `createdAt/updatedAt` 猜工程生效日期。全部采用明确时区的统一时间表示；禁止用本机字符串日期比较。校验区间倒置、非法时间及越界输入。

时间戳只回答时间，不充当跨记录的版本号。时钟回拨/同毫秒写入不改变 revision 顺序；独立分支/独立事实不能以同一时间戳推导先后。单记录并发修改仍靠现有 CAS/锁协议；跨记录没有因果证据时保留冲突，不自动拼成事务。

### 4.2 状态变更必须带明确目标

候选经人工确认后才进入确认事实；新事实可以显式替代旧事实，错误结论可以撤回。撤回不删除证据历史；再次生效需要新的显式确认，不能因旧摘要或缓存命中自动复活。

替代关系绑定“记录 ID + 被替代 revision/事实 ID + 适用范围”。`factKey` 用于识别同一业务属性，例如某需求的 PXE 默认值；身份字段、不同客户、不同板卡或分支不可只靠相同文字归并。

Board A rev1 的 PXE 关闭，Board B rev2 的 PXE 开启，可能各自正确。只有适用范围重叠且业务值冲突，才形成需处理的矛盾。客户名/厂商别名可用于检索，不能作为强身份合并依据。

既有 `deprecated` 是整卡退出默认推荐。首版不把“某一板卡条件被替代”误实现为整卡失效；细粒度替代未实现时，提供可见的待确认/冲突结果，不自动改整卡状态。

## 5. 当前事实与历史记录

提供两种明确的读取意图：

- `current`：服务当前目标工程，只给当前适用结论及其依据。
- `history`：显式查看被替代/撤回/旧状态，用于追踪原因；必须带历史标记，不混进当前执行建议。

首版历史查询只承诺已保存的语义变更；不是任意过去时刻的完整知识库快照。`asOfEffectiveTime` 与 `knownAtTime` 是不同问题，MVP 不开放未实现的任意双时间查询接口。

计划保留关键字段/需求/状态的**有界语义变更记录**，包含旧/新事实、目标版本、适用范围、依据、操作者声明和时间。优先放在所属业务记录的未来版本中，与当前状态用一次已有单记录提交共同保存；不要为每层再建一个事实来源。

变更历史大小有上限，超限拒绝本次写入并报告需要显式归档，不能静默丢掉撤回/替代关系。这里不要求保存每次聊天或整份源码快照，也不默认保存所有 JSON revision 的完整副本。

跨记录替代只有在完整读取双方、核对 ID/revision/范围/审核依据后才能参与当前事实计算；遇到半提交/缺记录/循环关系返回 unresolved，不回退到“旧事实有效”。首版先做同记录的状态/字段沿革，跨记录原子变更不在本期实现范围。

现有 review 审计/journal 证明的是既有审核操作与结果，**不是通用语义历史**。不能拿 journal v2 冒充业务 schema v2，也不能假称已有完整历史事实账本。

## 6. 工程快照与验证失效

适用性描述至少考虑：biosProjectId、customer/复用授权、workspaceId、IBV 及版本、Silicon 家族/代际、boardRevision、buildTarget；代码依据使用明确 commit 和必要的文件 hash。实际字段是否必需按事实类型定义，不要求每条通用经验都填所有平台字段。

仅记录 branch 名不够，同一 branch 的 HEAD 会变；非 Git 或未提交文件按相关文件 hash 绑定。commit 也不证明构建条件相同，验证需携带板卡/构建目标/关键配置范围。

- workspace 暂时不可达：证据 unavailable，不删除项目或宣布事实错误。
- 关键 hash/目标快照变化：验证 needs-review；历史测试结果保留，不冒称当前通过。
- 档案被人工替代：旧结论从 current 排除，历史仍可查。
- 未知字段：保持 unknown；请求补证据，不推测厂商或板卡。

不是任何无关文件变化都使全部知识失效；逐项比较该事实声明的依赖。无法判定相关性时标记不确定，不自动重扫整个源码树。

## 7. 检索与上下文决策路径

固定顺序：授权/模型端点策略 → 最新权威记录可读性 → 审核/退出状态 → 目标范围与生效条件 → 替代/撤回/冲突 → 证据与验证快照 → 关键词/别名匹配 → 可解释排序 → 预算选择。

这是一个有界策略管道，不要求每轮逐条扫描 2,000 个正文。候选索引只定位 ID；批量读取和核对仍有条目/字节/时间预算。预算不足要报告 incomplete，不能把“没读到矛盾”当成“无矛盾”。

未来如增加 RAG/向量索引：

- 保存 recordId、revision、scope、状态与索引依据 hash，不把向量库当权威存储。
- 范围过滤尽早执行；返回可见内容前重新核对权威记录。索引过旧时拒绝旧正文或显式降级为需复核，不推荐 deprecated/retracted 的旧结论。
- 权威记录损坏/不可读时不能改用缓存宣称事实有效；检索与重建不能修改事实状态。
- 更新/删除索引允许最终一致，但授权与当前有效性检查不能最终一致地放行旧材料。

每轮由当前项目/任务/代码依据生成 `ContextManifest`，固定来源记录 ID/revision/hash、选择理由、排除/过期原因和预算。继续使用 12,000 字符且 UTF-8 ≤24 KiB 的默认正文预算，不冒充 token 精度。

Manifest 是派生物，不批准事实。新一轮重验关键来源后替换上一轮 BIOS 上下文，不不断追加。历史 Session 文本无法抹去，但必须明确声明旧摘要是历史引用，当前权威状态优先；不能保证模型永不犯错，工具读取与动作前置检查也要使用当前记录。

无明确 taskId 只列任务摘要，不能续跑上次任务。任务由 done 重开为 in_progress 后，新 revision 的状态优先；旧交接摘要不得写回 done。上下文生成时发生版本变化应有界重试一次或返回 stale/incomplete；不能把来自不同时刻的记录伪装为一致快照。

冲突事实不进入“确定结论”块，进入待确认摘要；有关动作先暂停并请求人工确认，不自行选择 timestamp 最新的一条继续修改 BIOS。

## 8. 兼容与存储边界

现在仍是业务 schema v1、registry v1、audit/intent v1、journal v1/v2。**本次不升版，不向现有严格 schema 塞额外字段，不创建假迁移。**

BM-M1 先制定纯契约/决策规则，不碰用户磁盘。新增历史/时间字段需要 BM-M2 的独立变更方案：指定每个记录族源/目标 schema、转换规则、未知值语义、写入/审核协议影响、备份与恢复证据。只有该方案验收后才改实际 schema 和 C3 支持版本表。

v1 记录无法推导的工程时间/替代关系标为 unspecified，不伪造 `effectiveFrom=createdAt` 或硬件验证时间。兼容读取可继续展示已审核且授权范围匹配的旧经验作为参考，但不把未指定时态/快照的记录当当前已验证事实。现有 deprecated 始终排除默认推荐。

正式格式变更之前，纯解析器可以在内存中给 v1 候选加明确的 legacy 标签；它不是已迁移记录，不回写磁盘。未来新版支持仍须遵守旧版未知 schema 拒绝/保留原字节的规则。

继承当前单记录原子提交、revision 冲突、协作锁、不偷锁、取消/清理及审核授权。多记录一致性不能凭一个 timestamp 或一次预检保证；不引入通用事务系统作为本期前置。

## 10. 业务阶段验收矩阵

全部先用合成 fixture，不读取未经授权的客户资料。未实现阶段只记录待做，不计为测试通过。

| 编号 | 场景 | 应有结果 | 落地阶段 |
|---|---|---|---|
| MT-01 | 已确认字段与新检测候选冲突 | 保留原确认与新证据，标待复核，不自动覆盖 | M1、03 |
| MT-02 | 时钟回拨/同毫秒并发写 | revision 因果关系优先；独立事实冲突可见 | M1、M2 |
| MT-03 | 后录入旧测试、未来生效需求 | 录入时间不等于生效时间；未来规则不提前成为当前值 | M1、04 |
| MT-04 | Board A 的需求替代，Board B 未变 | 只影响指定事实/范围，不将另一板卡结论废弃 | M1、03/04 |
| MT-05 | 新 Session 命中已撤回事实的旧摘要 | current 不恢复该结论；history 显示撤回原因 | 04、05 |
| MT-06 | done 任务重开，旧交接仍说完成 | 新 revision 为 in_progress；旧写入冲突，不续跑旧完成结论 | 05 |
| MT-07 | 切分支/HEAD/板卡/构建目标 | 重新判断相关验证范围，不继承旧“已验证”保证 | 03、05 |
| MT-08 | 陈旧索引仍含 deprecated/retracted 材料 | 权威读取排除当前推荐，不返回无权摘要/计数 | 04；先用假索引 fixture，无需向量库 |
| MT-09 | 两会话提出重叠范围的矛盾结论 | 不按 timestamp 自动覆盖；CAS 冲突或语义冲突明确 | M1、04/05 |
| MT-10 | 证据不可达/损坏/相关 hash 变化 | unavailable/needs-review 可见，不以缓存兜底为事实 | 03～05 |
| MT-11 | 预算触顶/上下文组装中来源变更 | incomplete/stale 可见；不伪装完整一致快照 | 04、05 |
| MT-12 | v1 缺少生效时间，历史达到上限 | unspecified 不造假；超限拒写，不丢撤回/替代链 | M2、03～05 |

验收重点是可执行决策与跨会话磁盘读回，不只检查一段生成的提示词。BM-08 再用合法真实样例检验这些规则是否符合 BIOS 工作流，不能凭合成 fixture 宣称所有 IBV/Silicon 已适配。
